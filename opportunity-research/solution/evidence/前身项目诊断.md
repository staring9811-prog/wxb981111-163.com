# 前身项目诊断：现有采集与打标技能包（2026-10-26）

> 材料：用户上传的「爬取与打标技能包_含Lowes_HDP_20261026」（9 个技能 + Wayfair/Lowe's/HDP 项目代码）。只读，未运行任何采集脚本。

## 现有能力盘点

| 环节 | 技能 / 代码 | 做什么 |
|---|---|---|
| 调度 | market-research-ai-router | L0 规则代码 → L1 低成本模型 → L2 Claude Code → L3 Codex 定义与复核；付费调用、联网、批量前须人工确认 |
| Amazon 销量 | amazon-traffic-sales-estimator | 卖家精灵父体月销 × 子体流量词数占比 → 子体月销；附大量历史修正规则 |
| Lowe's 销量 | retail-product-review-research（lowes-sales-labels） | 周购买标签 N+ 按 N×30÷7 折算，BSR 分段线性插值/外推 |
| HDP / Wayfair 销量 | retail-product-review-research（review-sales） | 评论代理：HDP 为 VP×50+非VP×10；Wayfair/Lowe's 为 VP×30+非VP×10 |
| 打标 | bathroom-vanity-tagger、keyword-taxonomy-skill | 浴室柜 11 维（带逐字段证据）；关键词相关性 + 分类 + 打标 |
| 分析 | brand-matrix-heatmap、translate-pain-evidence | 尺寸×品牌×类型热力图；评论痛点 → 事件 → 频率/评分伤害/SKU 广度量化 |
| 质控 | table-schema-confirmation、table-macro-check | 任何表先逐列确认表头与选项；复杂表自动给"大数" |

## 诊断

### 1. 没有"判定机会"这一层（核心缺口）

全包检索未发现任何机会评分、属性溢价、趋势计算或"什么条件下立项"的规则。技能都止于"干净、带证据的表 + 热力图"。从表到"做什么产品"这一步，每次由 Agent 或产品经理临场完成。
→ 这正是"没有辨别出哪些核心指标、标准和动作"的直接原因：它们从来没有被写下来，也就无法被检验和复用。

### 2. 业务规则写在散文里，导致不稳定

关键口径以自然语言累积在 SKILL.md 和 references 里（多处"2026-10-21 补充""2026-10-22 用户确认"）。基础分摊脚本自己声明"未实现全部历史 SaleScope 修正规则或用户覆盖条件，不能直接当作完整规则执行器"。
→ 每次运行都要 Agent 重新理解几十条规则，同一输入可能得到不同结果。路由技能本身写了"规则固定的用代码（L0）"，但核心业务规则没有落到 L0。

### 3. 四个平台、四种"销量货币"

| 平台 | 销量口径 | 性质 |
|---|---|---|
| Amazon | 卖家精灵父体预测 × 流量词占比 | 第三方模型值 + 分摊假设 |
| Lowe's | 周购买标签 ×30/7 + BSR 线性插值 | 平台标签下界 + 插值模型 |
| HDP | 评论 VP×50 + 非VP×10 | 用户历史假设，未校准 |
| Wayfair | 评论 VP×30 + 非VP×10 | 用户历史假设，未校准 |

技能自己也写明系数"不是平台官方销量或已校准转化率"、不能混算渠道份额。
→ 框架里的"四平台并重、轨迹对比"目前只能比平台内的排序和份额，不能比绝对量。

### 4. 人工确认关口多，拉长周期

每张新表都要逐列确认表头和下拉选项；关键词分类要在类目节点停下等确认；付费/联网/批量调用前要确认。对数据安全有价值，但一次 20 天的研究里会产生大量往返。

### 5. 移植性差

代码依赖旧机器 D 盘绝对路径、Codex ↔ Claude Code 交接目录、Bright Data 令牌、会变化的 Wayfair GraphQL operation；HDP 灯镜结果曾因候选来源错误整体作废。

### 6. 没有验证集

估算规则文档明确："当前没有真实子体成交量验证集，不可宣称新增规则使准确率提升。"机会指标同样没有任何"当时判断 → 后来结果"的验证。

## 值得保留的资产

- 数据纪律与逐字段证据打标（质量高，可直接继承）；
- 已有确定性脚本：allocate_sales.py、estimate_lowes_sales.py、review_metrics.py、tag_cached.py、audit_event_identity.mjs；
- translate-pain-evidence 的痛点量化方法（频率、差评集中度、评分伤害、SKU 广度、结构偏差），可支撑框架 ② 和 4.2；
- 路由分级思想（L0–L3）本身是对的，只是没用到业务规则上。

## 对解题的含义

问题不在"缺数据"或"缺采集能力"，而在：
1. 缺一张固定、带版本的**机会判定卡**（指标 + 阈值 + 动作）；
2. 缺一个**验证回路**来挑出真正有用的指标；
3. 核心口径要从散文变成**代码**，Agent 只负责打标、解释和处理例外。
