## 1. 产品技术画像

### 1.1 产品形态

- 桌面浏览器网页，局域网内多人访问，三类角色（操作者 / 审批者 / 只读）。
- 运行在 wen 电脑上（Windows 或 Mac），双击启动。
- 并入两个已有工具：
  - 评论月度 VP 追踪器：Python，`reviewkit`；
  - 利润测算台：单页 HTML，计算逻辑在前端。

### 1.2 核心技术约束

| 约束 | 来源 | 对技术的影响 |
| :--- | :--- | :--- |
| 局域网共享、只在 wen 电脑运行 | KD-R2-01；NFR-007 | 单进程单实例；监听局域网地址，不暴露公网 |
| 账号密码、三类角色、停用即失效 | REQ-F15-01、REQ-F15-02 | 服务端会话；每次请求都校验账号状态 |
| 密钥本机加密存储、只显示后 4 位 | REQ-F16-01；NFR-008 | 本机密钥文件加密；日志和导出脱敏 |
| 花钱前先评估、月度上限、记账 | REQ-F16-02 | 所有外部调用都经过统一的"费用闸门"模块 |
| 卖家精灵按月拉、断点续拉、不重复计费 | REQ-F17-01；NFR-011 | 任务分片、记录完成状态，幂等重跑 |
| 月份误标 / 来源切换核对 | REQ-F17-02 | 并入前跑核对规则，异常需人工确认 |
| 打标 + 看图 + 确认队列 | REQ-F18-01～03 | 规则引擎沿用第二轮打标技能；大模型多家可选 |
| 第九版评分、回测 | REQ-F19-01、REQ-F19-02 | 复用 `solution-v2/trial/` 的 pandas / scikit-learn / statsmodels 计算 |
| 分渠道扫描、评论换算销量、同系列去重 | REQ-F28、REQ-F29 | 数据模型带"渠道"字段；评论按评论 ID 去重 |
| 决策卡批准后快照 | AC-F25-02 | 卡片数字以快照形式存储 |
| 扫描 10 秒内出结果、决策卡 30 秒内生成 | NFR-009、NFR-010 | 每月并入后预算并缓存单元级结果 |
| 数据保留 36 个月 | NFR-012 | SQLite 单文件；按月版本化 |

### 1.3 团队与规模画像

- 实现由 AI / Coding Agent 负责；用户约 5–10 人，同时在线 ≤ 5 人；第一版只有一个品类。
- 数据量：24 个月约 5 万行子体 × 月（Amazon），加上其他渠道 650 个商品、1.5 万条评论 / 10 个月；每年新增约数万行。

### 1.4 非功能性需求

- NFR-007：局域网访问。
- NFR-008：密钥只在本机。
- NFR-009：扫描 ≤ 10 秒。
- NFR-010：决策卡 ≤ 30 秒。
- NFR-011：断点续跑不重复计费。
- NFR-012：保留 36 个月。

**外部服务说明**：卖家精灵、Bright Data、Apify、大模型（Claude / OpenAI 等）都是用户在 PRD 和蓝图 §7 中确认的业务依赖，不是本方案新增的推荐。其中 Bright Data、Apify、Anthropic、OpenAI 是海外服务，可达性取决于 wen 的网络环境。现有评论 VP 追踪器已在使用 Bright Data、Apify。大模型接入兼容 OpenAI 协议，可以填自定义地址，因此也能接国内兼容服务，作为可达性后备。

## 3. 前端技术选型

### 3.1 候选方案对比

| 候选 | 适配本期 | AI 生成稳定性 | 与现有原型 / 工具的复用 | 复杂度 | 加权 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| 服务端渲染（Jinja2 3.1.6）+ 原生 JS | 5 | 5 | 5（原型就是静态 HTML + app.css；利润测算台本身是原生 JS） | 5 | **5.0** |
| React 单页应用 + 构建流程 | 3 | 4 | 2（要重写原型和利润测算台） | 2 | 2.8 |

### 3.2 推荐：服务端渲染（Jinja2）+ 原生 JS

- **理由**：
  - 页面以表格、表单为主，原型可以直接改成模板；
  - 不需要前端构建，wen 双击即可运行；
  - 利润测算台原样嵌入，只把 localStorage 换成后端接口（AC-F24-02）。
- **交互**：
  - 长任务进度用轮询，每 2 秒一次，不引入 WebSocket；
  - 图表用内联 SVG 生成，不新增图表库；
  - 利润测算台原有的 xlsx.full.min.js 0.18.5 改为本地文件。
- **代价**：交互复杂度上限较低。**升级触发**：页面出现需要大量客户端状态的交互，例如多人实时协作编辑。

### 3.3 风险与缓解

- 利润测算台并入时出现计算回归。缓解：并入前用原工具导出若干方案作为基准，逐项比对（AC-F24-01 的不变行为）。

## 4. 后端技术选型

- **推荐（直接默认，沿用第一轮与蓝图 §8）**：Python 3.12+、FastAPI 0.162.0、Uvicorn 0.54.0，单进程运行，监听局域网地址。
  - 证据：第二轮全部计算脚本（`solution-v2/trial/`）和评论 VP 追踪器都是 Python，可以直接并入为模块。
  - 代价：单进程同时只能跑一个重任务。
  - 升级触发：要迁到服务器或多用户并发重任务。
- **模块边界**：业务计算放在 `core/`，不引用 Web 框架，便于 TDD 单测；Web 层只负责路由、模板、权限和任务调度。
- **费用闸门（核心组件）**：
  - 所有外部调用（卖家精灵、Bright Data、Apify、大模型）都走同一个闸门；
  - 闸门流程：先估算，wen 确认后取得当月额度，执行时逐笔记账，到上限即停（AC-F16-06～08）；
  - 评论 VP 追踪器原有的分平台预算和 `ledger.json` 改接到这个闸门。
- **后台任务**：
  - 进程内单 worker 队列；任务状态存在 SQLite；
  - 分片完成即落库，重跑时跳过已完成分片（NFR-011）；
  - 同一月份的同类任务互斥。
- **关键时序**：

## 5. 数据层选型

### 5.1 主数据库

- **推荐（直接默认）**：SQLite 单文件（WAL 模式），SQLAlchemy 2.1.6 + Alembic 1.20.1 管理表结构。
  - 理由：单机单实例、≤ 5 人同时在线、数据量为几十万行级；备份就是复制文件。
  - 代价：不适合多实例。升级触发：迁服务器或多实例时换 PostgreSQL。由于用 SQLAlchemy，迁移成本可控。
- **核心实体**（DATA-F15-01 起编，全部带"品类"和"渠道"字段，这是不可逆约束）：
  - 账号与会话；
  - 密钥（只存加密后的值）；
  - 预算与费用记录；
  - 拉取任务与分片；
  - 月度数据批次（核对结果、* 标记）；
  - 商品（子体 / 家族 / 系列）；
  - 月度快照；
  - 标签与确认记录（来源：规则 / 看图 / 人工）；
  - 单元评分（版本化）；
  - 回测结果；
  - 机会；
  - 决策卡、卡片版本与快照；
  - 评论与归类；
  - 利润方案；
  - 审批；
  - 策略库条目与版本；
  - 台账；
  - 品类配置（分框、属性、打标规则、渠道系数、成功线，版本化）；
  - 审计日志。
- **状态机**（决策卡，F21 / F25 / F26）：
  - 合法迁移：草稿 → 待审批 → 已批准 / 已驳回 / 退回草稿；已批准 → 跟踪中 → 已对账。
  - 非法迁移：已批准后再编辑数字。只能"另存为新草稿"（AC-F25-02）。
  - 并发：审批与编辑同时发生时，以审批时间点锁定的版本为准。

### 5.2 缓存层（如激活）

- 不引入独立缓存。每月并入后，预算好单元级评分和扫描结果并存表，满足 NFR-009。

### 5.3 搜索引擎（如激活）

- 不激活。列表筛选直接用 SQLite 查询。

### 文件存储

- 单实例、本机持久化磁盘：原始拉取文件、上传文件、导出文件、商品图片缓存都放在 `data/` 目录下，约几 GB 级。不引入对象存储。
- **备份**（蓝图 §9）：每次并入数据、每次审批后，用 SQLite 在线备份生成带时间戳的副本，保留最近 30 份。RPO 等于上次并入或审批的时刻，RTO 为分钟级（换回备份文件即可）。

## 6. AI 能力选型

### 6.1 LLM 选型

- **用在哪**：看图打元素（多模态）、差评归类、决策卡叙述草稿。全部是单轮调用，不打分（方案书原则）。
- **推荐**：
  - 设置页可选提供方（AC-F16-04），用官方 SDK（anthropic 2.4.0、openai 3.42.1）；
  - OpenAI 协议支持自定义地址，可接其他兼容服务；
  - 默认推荐 Claude：第二轮的看图补标和差评归类都是用 Claude 做的，口径一致。具体型号在设置页选择，不写死。
- **输出**：要求结构化输出（JSON），带置信度；解析失败或低于阈值的进入人工确认（AC-F18-03）。
- **费用**：每次调用前估算 token 量，走费用闸门。

### 6.2 检索方案（如需 RAG）

- 不适用。

### 6.3 Agent / 编排框架（如需多步推理）

- 不需要。三类用途都是单轮调用，加上代码里的确定性流程；不引入 Agent 框架。

### 6.4 Embedding 模型

- 不适用。

## 7. 基础设施选型

### 7.1 部署与托管

- wen 电脑本机运行。
- 提供"启动.bat / 启动.command"，沿用两个工具的做法：首次运行自动建虚拟环境、安装依赖；启动后打开浏览器，并显示局域网访问地址。
- 只监听局域网网卡，不做公网映射。

### 7.2 认证与授权

- 账号密码，argon2 哈希；会话 Cookie（HttpOnly、SameSite=Lax），有效期 7 天。
- 每次请求都检查账号是否停用（AC-F15-05）。
- 角色权限在服务端统一校验（AC-F15-02、03）；界面上没有权限的入口直接隐藏。
- 局域网内为 HTTP，接受这个代价。如果以后要跨网访问，再加 HTTPS。

### 7.3 可观测性

- 运行日志写本地文件，按天滚动；密钥、密码脱敏。
- 审计日志表记录登录、审批、密钥变更、花钱任务，在账号页可查看。

### 7.4 CI/CD

- 第一版不做 CI。交付形式为仓库代码加启动脚本，TDD 验收用本地测试命令。

### 7.5 条件能力（按需激活）

- **定时任务**：不激活（RA-101：所有花钱任务由 wen 发起）。
- **导出**：Excel 用 openpyxl。
- **图片**：商品主图按需下载并缓存到本地，供看图打标和 SKU 展开使用。

## 8. 实施建议与风险全景

### 8.1 推荐技术栈一览（最终决断）

| 层 | 选型 |
| :--- | :--- |
| 运行环境 | Python 3.12+（本环境 3.13.17 已验证可用），wen 电脑，局域网 |
| Web | FastAPI 0.162.0 + Uvicorn 0.54.0 + Jinja2 3.1.6 + 原生 JS |
| 数据 | SQLite（WAL）+ SQLAlchemy 2.1.6 + Alembic 1.20.1；本地 data/ 目录 |
| 计算 | pandas 3.1.0、scikit-learn 1.9.1、statsmodels 0.15.0、openpyxl 3.1.5 |
| 安全 | argon2-cffi 25.1.0、cryptography 50.0.2 |
| AI | anthropic 2.4.0、openai 3.42.1（兼容自定义地址） |
| 并入 | reviewkit（评论 VP 追踪器）作为模块；利润测算台前端原样嵌入 |

### 8.2 本期实施起步建议

1. 先建骨架：登录与角色、设置页（密钥、费用闸门）、SQLite 表结构。
2. 并入两个工具，先保证原功能不变：
   - 用原工具输出做基准比对；
   - reviewkit 的预算改接费用闸门。
3. 数据链路：卖家精灵拉取 → 核对 → 打标 → 确认队列；其他渠道评论并入 → 销量估算。
4. 分析：把 `solution-v2/trial/回归预测.py`、`回归预测_第九版.py`、`机会扫描.py`、`决策卡.py` 的计算移入 `core/`，用第二轮的结果做回归基准。
5. 决策卡、差评、利润回写、审批、台账。

### 8.3 后续阶段扩展预留

- 加品类、加渠道：数据表已带品类和渠道字段，配置版本化（F27）。
- 迁服务器：SQLAlchemy 换 PostgreSQL，加 HTTPS；业务模块不变。
- 定时自动拉取：费用闸门已有"上限内自动执行"的接入点，只是第一版不开启。

### 8.4 全局风险与缓解

| 风险 | 影响 | 缓解 |
| :--- | :--- | :--- |
| 卖家精灵接口不能稳定拉全量 | 高 | 断点续拉；手动上传后备；核对能发现缺失 |
| 海外服务（Bright Data、Apify、大模型）在本机网络下不稳定 | 中 | 设置页"测试"及时暴露；大模型可换兼容地址；失败只影响对应功能 |
| 第二轮计算脚本移入产品时口径漂移 | 高 | 以第二轮结果文件为基准，做数值回归测试 |
| 利润测算台并入后计算变化 | 中 | 原工具导出方案作为基准比对 |
| wen 电脑关机时其他人访问不到 | 低 | 已接受（PRD 关键决策） |

### 8.5 技术负责人的最终结论

#### 是否可以立即开工

可以。全部依赖已确认，版本已核实，没有需要新增的外部服务。

#### 最大的技术不确定性

卖家精灵接口能否稳定拉取浴室柜类目的全量月度数据，以及看图打元素的准确率。

#### 现在最不应该做的事

- 引入前端构建、独立缓存、Agent 框架或定时任务；
- 在分框规则之外"优化"第二轮已验证的口径。
